Schema names as reported by the backend agent on 2026-11-26 (renamed to avoid clashing with Expenses; **still to
confirm against the generated file in EN-001**), used through `Schema<'…'>`: `GiftItem`, `GiftVariantItem`,
`GiftRequest`, `GiftVariantRequest`, `GiftStatusRequest` (`status`, `giftedOn?`), `GiftCategoryItem`,
`GiftDetailItem`, `GiftsSummary` (`recipients[{ recipient, counts: GiftCounts, topWanted: SummaryGift[] }]` always in
the order Maria, Vitaliy, Together; `total: GiftCounts`; `upcoming: UpcomingOccasion[]`; `details: GiftDetailItem[]`),
`GiftCounts`, `SummaryGift`, `UpcomingOccasion`, and `CreatedGiftsEntry` (`{ id }`, the create answer). Variant ids
are regenerated on every gift update; a `giftedOn` sent with a non-Gifted status is ignored; a repeated `Gifted`
keeps the existing day. Extra codes: `gifts.link_invalid`, `gifts.price_invalid`, `gifts.variant_invalid`,
`gifts.too_many_variants`.

Lists (`listGifts`, `listGiftCategories`, `listGiftDetails`) return bare arrays (backend SDD). Category rename
and delete take no `If-Match` (categories carry no version); gift, status and detail edits do.
`GiftsSummary` shape per the backend SDD: `recipients[{ recipient, counts, topWanted[] }]`, `total` (counts),
`upcoming[]`, `details[]`; `counts` = `wantedCount`, `wantedPriceSum`, `wantedWithoutPrice`, `highCount`,
`giftedCount`, `giftedPriceSum`.

## Client projection

- Defaults and request checks: [data-model.md](../data-model.md); the server checks again and its field errors win
  on their fields.
- Runtime validation of responses: none (as the rest of the app); generated types are compile-time only.
- Paging, sorting, filtering: none on the server except `archived`; order is the server's; filters are client-side.
- Cache owner and keys: React Query, keys in [frontend.md](../design/frontend.md#state-and-data); default stale time
  of the shared query client; invalidation after writes.
- Retries, cancellation, duplicates: GETs pass `signal`; 4xx not retried; creates use one `Idempotency-Key` per opened
  form and data, reused on retry, renewed after success, a data change or `idempotency_key_reused`
  ([rules, Writes](../../../../rules.md#writes)); every submit is disabled while pending; the quick status buttons
  are disabled for that card while its request is pending.
- Auth and permissions: ➖ none (API ADR 0015); writes are rate limited (429 handled).
- Rollout: API first, then `contracts:generate`, then web (AGENTS.md merge order).

## Contract verification

- `cd web && npm run contracts:generate` after the backend change is on the branch; commit the generated file with the
  web change; `npm run contracts:check` must pass.
- Reproducible from the pinned provider revision recorded in EN-001.
- Focused tests: `write-errors-api.test.ts` (every status/code → text), page tests assert request method, path,
  `Idempotency-Key`, `If-Match` and body.
- Fixtures: inline JSON in the page tests, shaped like the generated types (typed against `Schema<>` where practical).
